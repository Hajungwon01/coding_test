## 💻 문제 설명

### 압축
신입사원 어피치는 카카오톡으로 전송되는 메시지를 압축하여 전송 효율을 높이는 업무를 맡게 되었다. 메시지를 압축하더라도 전달되는 정보가 바뀌어서는 안 되므로, 압축 전의 정보를 완벽하게 복원 가능한 무손실 압축 알고리즘을 구현하기로 했다.

어피치는 여러 압축 알고리즘 중에서 성능이 좋고 구현이 간단한 **LZW**(Lempel–Ziv–Welch) 압축을 구현하기로 했다.

### LZW 압축 과정
1. 길이가 1인 모든 단어를 포함하도록 사전을 초기화한다.
2. 사전에서 현재 입력과 일치하는 가장 긴 문자열 `w`를 찾는다.
3. `w`에 해당하는 사전의 색인 번호를 출력하고, 입력에서 `w`를 제거한다.
4. 입력에서 처리되지 않은 다음 글자가 남아있다면(`c`), `w+c`에 해당하는 단어를 사전에 등록한다.
5. 단계 2로 돌아간다.

### 입출력 예제
| msg | answer |
| :--- | :--- |
| `KAKAO` | `[11, 1, 27, 15]` |
| `TOBEORNOTTOBEORTOBEORNOT` | `[20, 15, 2, 5, 15, 18, 14, 15, 20, 27, 29, 31, 36, 30, 32, 34]` |
| `ABABABABABABABAB` | `[1, 2, 27, 29, 28, 31, 30]` |

## 📌 1. 첫 번째 접근: 스택(Stack)? (시행착오)
처음에는 문자열을 하나씩 쌓아가며 비교해야 하나 생각하여 **스택(Stack)** 자료구조를 먼저 떠올렸습니다. 
하지만 LZW 압축 알고리즘의 핵심은 **"현재 인덱스에서 시작하는 사전 속 가장 긴 단어를 탐색하는 것"**이었기 때문에, 후입선출(LIFO) 구조의 스택은 이 문제의 본질인 '가변적인 전방 탐색'과 맞지 않음을 인지하고 빠르게 방향을 선회했습니다.

## 📌 2. 두 번째 접근: 투 포인터와 슬라이딩 윈도우 (AI 협업 및 디버깅)
기본 알파벳이 담긴 사전(`dict`) 구조를 유지하면서, 문자열을 탐색할 두 개의 포인터 `left`와 `right`를 활용해 인덱스를 동적으로 제어하는 방식을 채택했습니다. 이 과정에서 **AI와의 질의응답을 통해 정답 코드 조각을 복사하지 않고, 오직 논리적인 힌트만을 얻어 스스로 디버깅을 진행**했습니다.

### 🚨 디버깅 과정에서 마주한 인덱스 버그와 해결

#### 1) 무한 루프와 인덱스 고정 문제 (AI 피드백 반영)
* **원인:** 안쪽 `while`문 내부에서 `right` 값을 매번 `left + 1`로 초기화해 버리는 바람에 `right` 포인터가 앞으로 전진하지 못하고 제자리걸음을 반복했습니다.
* **AI의 조언:** `right` 초기화 위치가 안쪽 루프 내부인지 바깥쪽 루프 내부인지 논리적 흐름을 점검하라는 힌트를 받았습니다.
* **해결:** 초기화 코드를 안쪽 루프가 시작되기 직전으로 빼내어 인덱스가 정상적으로 누적·증가하도록 수정했습니다.

#### 2) `left` 포인터 점프 제어 오류 (`left = right + 1` ➔ `left = right - 1`)
* **원인:** 사전에 없는 문자열을 만나 루프를 탈출했을 때, 다음 탐색 시작점인 `left`를 `right + 1`로 과도하게 지정하면서 처리해야 할 문자들을 통째로 건너뛰는 현상이 발생했습니다. 파이썬의 슬라이싱(`msg[left:right]`) 범위를 다룰 때 생기는 미세한 계산 오차였습니다.
* **AI의 조언:** 사전에 없는 단어를 만나 튕겨 나온 시점에서 `right` 포인터가 가리키고 있는 위치와, 실제 매칭에 성공한 단어의 최종 인덱스 간의 관계를 시뮬레이션해 보라는 단서를 얻었습니다.
* **해결:** 다음 탐색의 시작점은 `right - 1`이 되어야 함을 깨닫고 수식을 수정해 중복이나 누락 없이 탐색하게 만들었습니다.

#### 3) 빈 문자열(`''`) 슬라이싱과 문자열 끝 예외 처리
* **원인:** `right = left`에서 검사를 시작하면 최초에 빈 문자열이 나와 사전에 등록되는 예외가 발생했습니다. 또한, 문자열의 마지막 글자가 사전에 이미 존재할 때 루프 조건 범위(`right < len(msg)`)에 걸려 출력이 누락되는 현상이 있었습니다.
* **해결:** 안쪽 `while`문의 범위를 `right <= len(msg)`로 안전하게 늘려주고, 내부 진입 후 `right += 1`을 통해 슬라이싱 범위가 최소 한 글자 이상이 되도록 유기적으로 제어했습니다.

## 📌 3. 최종 코드 흐름 요약

1. **사전 초기화:** `dict` 컴프리헨션과 `chr()`을 이용해 `A-Z`까지의 기본 사전을 구축합니다.
2. **바깥쪽 루프 (`while left < len(msg)`):** 현재 압축을 시작할 글자의 위치(`left`)를 고정합니다.
3. **안쪽 루프 (`while right <= len(msg)`):** `right`를 1씩 늘려가며 사전에 단어가 있는지 확장 검사합니다.
   - 사전에 **있다면**: 가장 긴 단어의 색인 번호를 `tmp_n`에 계속 업데이트합니다.
   - 사전에 **없다면**: 새롭게 발견된 단어이므로 사전에 추가(`num + 1`)하고 안쪽 루프를 탈출(`break`)합니다.
4. **인덱스 점프:** 매칭 완료된 색인 번호를 결과 배열에 추가하고, `left`를 `right - 1`로 한 번에 점프시켜 다음 단어부터 압축을 이어 나갑니다.

## 💡 느낀 점 및 AI 협업 회고
단순히 `for`문으로 요소를 순차 순회하는 것을 넘어, **`while`문 안에서 두 개의 포인터를 조작해 탐색 범위를 동적으로 가변시키는 인덱스 제어 테크닉**을 제대로 연습할 수 있었습니다. 

특히 이번 문제는 정답 코드를 찾아보거나 AI에게 코드를 짜달라고 요구하지 않고, **"이 로직이 왜 무한 루프가 걸리는지", "인덱스 이동 수식이 왜 어긋나는지"에 대해 AI와 대화하며 힌트를 기반으로 직접 코드를 수정**해 나갔습니다. 이 과정을 통해 슬라이싱 범위의 미세한 오차가 왜 버그로 이어지는지 머릿속으로 완벽히 디버깅 규칙을 정립할 수 있었던 아주 값진 경험이었습니다.
